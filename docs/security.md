# Безопасность TZ-Opti (production baseline)

Минимальный, но полный контур защиты портала: **кто** обращается, **что** ему
можно, **чьи** это данные, **что произошло** и **что попало на диск**.

Главное правило всего контура — **fail-closed**: при любой неоднозначности
(нет правила доступа, не настроен антивирус, не проверился сертификат,
недоступен провайдер токенов) система отказывает, а не «пропускает на всякий
случай». Небезопасная конфигурация production не работает молча — она
**роняет старт** (`server.js` → `assertProductionSecurity`).

Все переменные окружения — в `.env.example`, блок «БЕЗОПАСНОСТЬ».

---

## 1. Карта модулей

| Файл | За что отвечает |
| --- | --- |
| `server/security/config.js` | env → замороженная конфигурация + проверки production (что обязано ронять старт) |
| `server/security/jwt.js` | проверка подписи и утверждений JWS/JWT (`node:crypto`, без внешних библиотек) |
| `server/security/keyStore.js` | источник ключей: OIDC discovery, JWKS, статический ключ, общий секрет; кэш и защита от DoS на IdP |
| `server/security/principal.js` | клеймы → субъект (тенант, роли, права) |
| `server/security/authenticator.js` | сборка: токен → principal (подменяется целиком в тестах) |
| `server/security/roles.js` | роли и матрица прав (чистый модуль) |
| `server/security/policy.js` | таблица «метод + путь → право, действие, источник тенанта», **default deny** |
| `server/security/tenantAccess.js` | тенант ресурса ИЗ БД + сверка с тенантом токена |
| `server/middleware/*` | requestContext, securityHeaders, corsPolicy, rateLimit, authenticate, authorize, auditLogger, upload, errorHandler |
| `server/services/audit/auditService.js` | журнал аудита (запись, чтение в пределах тенанта, чистка) |
| `server/services/uploads/fileSafety.js` | форматы, магические байты, SHA-256 |
| `server/services/uploads/antivirus.js` | обязательный антивирусный хук (clamd / command / http) |

Внешних зависимостей ради этого контура **не добавлено ни одной**: проверка
подписи — на `node:crypto`, заголовки, CORS и лимитер — свои маленькие
middleware. Причина практическая: дерево зависимостей репозитория сейчас не
устанавливается без `--legacy-peer-deps` (конфликт `zod` у `openai`), и
безопасность не должна зависеть от разрешения этого конфликта.

## 2. Порядок middleware = модель безопасности

`server/app.js`, сверху вниз:

1. **requestContext** — `X-Request-Id` (входящий принимается, только если похож
   на идентификатор) и IP клиента; нить между логом, аудитом и ответом.
2. **securityHeaders** — CSP `default-src 'none'` + `sandbox`, `nosniff`,
   `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-*`,
   `Cache-Control: no-store`, HSTS (только production поверх https).
3. **corsPolicy** — allowlist источников; чужому источнику CORS-заголовки не
   выдаются вовсе, preflight → 403.
4. **rateLimit.byIp** — общий лимит и счётчик неудачных аутентификаций, **до**
   проверки токена.
5. **auditLogger** — вешает запись журнала на завершение ответа.
6. **authenticate** — `Authorization: Bearer` → `req.principal`, иначе 401.
7. **authorize** — право роли, затем тенант ресурса, иначе 403.
8. **rateLimit.byAction** — лимиты дорогих действий, уже по субъекту.
9. **body parsers** — тело разбирается только у прошедшего проверки запроса.
10. маршруты → 404 → **errorHandler** (в production без внутренних деталей).

Единственный публичный маршрут — `GET /api/health` (отдаёт только `{ok, ts}`).

## 3. Аутентификация: JWT/OIDC без привязки к провайдеру

Режим определяется тем, **что задано** в окружении:

| Задано | Режим | Когда применять |
| --- | --- | --- |
| `AUTH_OIDC_ISSUER` | `oidc` | обычный случай: Keycloak, Entra ID, Auth0, Google — discovery + JWKS |
| `AUTH_JWKS_URI` | `jwks` | провайдер без discovery-документа |
| `AUTH_JWT_PUBLIC_KEY` / `_FILE` | `public_key` | ключ выдан «на бумаге» (PEM, JWK или JWKS-документ) |
| `AUTH_JWT_HS_SECRET` | `secret` | простой стенд с общим секретом (HS256) |

Что проверяется у каждого токена (`security/jwt.js`):

* формат JWS из трёх частей (JWE отвергается сознательно);
* `alg` из allowlist; **`alg: none` запрещён**;
* **alg-confusion невозможна**: семейство алгоритма обязано совпадать с типом
  ключа, HS* проверяется только симметричным секретом, а `kty: oct` из JWKS
  отбрасывается;
* подпись (RS/PS/ES; для ECDSA — формат P1363, как требует JWS, DER не пройдёт);
* `iss` — точное сравнение (без «вхождения подстроки»), `aud` — пересечение со
  списком, `exp` обязателен, `nbf`/`iat` с перекосом часов `AUTH_CLOCK_SKEW_SEC`;
* заголовок `crit` не поддерживается → отказ.

Утверждения проверяются **после** подписи: иначе по разным кодам ошибок можно
было бы изучать содержимое неподписанных токенов.

**JWKS.** Ключи кэшируются `AUTH_JWKS_CACHE_SEC`. Неизвестный `kid` вызывает
досрочный перезапрос **не чаще** `AUTH_JWKS_MIN_REFETCH_SEC` — иначе поток
токенов с выдуманными `kid` превращается в усилитель запросов к IdP. `jwks_uri`
обязан быть на том же хосте, что и issuer, и по https (http — только вне
production). Если провайдер недоступен, а кэш есть — работаем на кэше.

**Токен принимается только из заголовка** `Authorization: Bearer`. Ни query
(`?access_token=`), ни cookie: первое оседает в логах прокси и истории браузера,
второе тянет за собой CSRF.

**Причина отказа наружу не раскрывается** — в теле всегда «Требуется
аутентификация»; конкретика (истёк / чужой issuer / плохая подпись) уходит в
журнал аудита и лог.

### Dev-bypass

`AUTH_DEV_BYPASS=1` выдаёт фиктивного субъекта без токена. Работает **только
вне production** и проверяется дважды: при сборке конфигурации
(`devBypass.enabled = requested && mode !== 'production'`) и при выдаче
principal. В production сам факт `AUTH_DEV_BYPASS=1` — **ошибка старта**.

## 4. Роли и права

Роли: `viewer`, `engineer`, `lead`, `manager`, `admin`. Роль — это набор прав;
иерархии «по номеру» нет (manager не «больше» инженера, у него другая работа).

| Право | viewer | engineer | lead | manager | admin |
| --- | :-: | :-: | :-: | :-: | :-: |
| `tender.read`, `document.read` | ✅ | ✅ | ✅ | ✅ | ✅ |
| `tender.create`, `tender.update` | — | ✅ | ✅ | ✅ | ✅ |
| `tender.delete` | — | — | ✅ | — | ✅ |
| `document.upload`, `document.delete` | — | ✅ | ✅ | — | ✅ |
| `setup.write` (чек-лист, условия, риски, Q&A, параметры) | — | ✅ | ✅ | — | ✅ |
| `analysis.run` (стадии, конвейер, очередь, переимпорт ВОР) | — | ✅ | ✅ | — | ✅ |
| `decision.write` (решения по кластерам и находкам) | — | ✅ | ✅ | — | ✅ |
| `export.perform` (.docx, csv/json/md, preview, Q&A) | — | ✅ | ✅ | ✅ | ✅ |
| `audit.read` | — | — | ✅ | ✅ | ✅ |
| `admin.system` (статистика очереди) | — | — | — | — | ✅ |

Роли провайдера отображаются в роли портала через `AUTH_ROLE_MAP`
(`tz-opti-heads:lead,tz-opti-engineers:engineer`). **Всё, что не отобразилось в
известную роль, прав не даёт**; субъект вообще без известной роли получает 403
`NO_ROLES` — повторная аутентификация тут не поможет, поэтому не 401.

`GET /api/auth/me` отдаёт субъекта, его роли и права — по нему клиент прячет
кнопки, решение всё равно принимает сервер.

### Таблица доступа (default deny)

`security/policy.js` описывает каждый маршрут: право, действие для аудита,
категория и источник тенанта. **Пути без правила запрещены** (403
`POLICY_UNMATCHED`) — новый маршрут не заработает, пока для него не появится
строка. За этим следит тест `security/policy.test.js`: он обходит все
зарегистрированные маршруты приложения и требует правило для каждого.

## 5. Изоляция тенантов

Тенант = организация. `tenders.tenant_id` — ключ изоляции, всё остальное
(документы, находки, кластеры, решения, задания) наследует тенант **через
тендер**.

* Тенант субъекта — **только из токена** (`AUTH_CLAIM_TENANT`). Тело запроса,
  query и заголовки на принадлежность не влияют: `POST /api/tenders` с
  `tenant_id` в теле создаст тендер в тенанте токена.
* Тенант ресурса — **только из БД** (`security/tenantAccess.js`, один JOIN к
  `tenders` для дочерних сущностей: документ, находка, характеристика, задание).
* Списки ограничены тенантом на уровне SQL (`WHERE tenant_id = ?`), а не
  фильтрацией «после выборки».
* Удаление тендера дополнительно повторяет условие по тенанту в самом `DELETE` —
  второй рубеж там, где ошибка необратима.

**Межтенантное обращение → 403 `CROSS_TENANT_DENIED`** (не 404). Идентификаторы
— UUID v4, перебором их не найти, поэтому скрывать существование смысла нет,
зато явный отказ виден в журнале и понятен поддержке. Ресурс, которого нет
вовсе, даёт 404. Неаутентифицированный запрос к чужому и к несуществующему
тендеру отвечает одинаково — до проверки токена о ресурсах не сообщается ничего.

Миграция заводит `tenants`, добавляет `tenders.tenant_id` и переносит
существующие тендеры в `SECURITY_DEFAULT_TENANT` (по умолчанию `default`).

## 6. Журнал аудита

Таблица `audit_log`; сервис `services/audit/auditService.js`; запись вешается на
завершение ответа (`middleware/auditLogger.js`).

Пишется: **чтение** (можно отключить `AUDIT_LOG_READS=0`), **изменения**,
**запуск анализа**, **решения**, **выгрузки** и **любой отказ** (401/403/429).

В записи: время, `request_id`, тенант, субъект (`sub`, почта, роли на момент
действия), способ аутентификации, действие (`stage.run`, `review.cluster.decide`,
`export.docx`…), категория, исход (`allowed|denied|error`), ресурс, тендер,
метод, путь (**без query** — там бывают поисковые строки), статус,
длительность, IP, user-agent, причина отказа и `meta` (например SHA-256 файла и
вердикт антивируса). Токен в журнал не попадает ни целиком, ни частями.

Запись **best-effort**: недоступный журнал пишет ошибку в лог, но не откатывает
уже выполненную операцию инженера. Чтение — `GET /api/audit` (право
`audit.read`), **всегда** в пределах тенанта из токена, с фильтрами
(`tender_id`, `actor`, `action`, `category`, `outcome`, `since`, `until`).
Чистка по сроку хранения — `auditService.purgeOlderThan` (`AUDIT_RETENTION_DAYS`).

## 7. Транспорт: CORS, заголовки, лимиты, ошибки

**CORS.** Только allowlist (`CORS_ALLOWED_ORIGINS`), сравнение по
`протокол+хост+порт` — ни поддомен, ни подстрока совпадением не считаются. Есть
`Vary: Origin`. Запрос без `Origin` (curl, серверные вызовы) не блокируется:
CORS защищает браузерного пользователя, а не сервер. В production пустой список
и `*` — ошибка старта.

**Ограничение частоты.** Фиксированное окно в памяти процесса: общий лимит по
IP, отдельный счётчик неудачных аутентификаций (после `RATE_LIMIT_AUTH_FAIL_MAX`
адрес отсекается до конца окна — защита от подбора токена) и лимиты дорогих
действий по субъекту (загрузка, анализ, выгрузка). Ответ — 429 с `Retry-After` и
заголовками `RateLimit-*`.
**Ограничение честное:** счётчики локальны для процесса, при нескольких
инстансах фактический лимит умножается на их число. Это защита от «цикла в
скрипте» и подбора, а не замена лимитера на входном прокси; общий стор
(Postgres/Redis) — точка расширения `createStore()`.

**X-Forwarded-For** учитывается только на `RATE_LIMIT_TRUST_PROXY_HOPS`
последних звеньев; по умолчанию 0 — заголовок игнорируется целиком.

**Ошибки.** В production наружу уходит текст только доменных (4xx) ошибок;
5xx схлопываются в «Внутренняя ошибка сервера» + `request_id`. Сообщения
драйвера БД, пути на диске, имена переменных и строки подключения не выходят
никогда — они остаются в логе, найти их можно по тому же `request_id`.

## 8. Загрузка файлов

Файл идёт **через карантин**: `uploads/quarantine/` → проверки → папка тендера.
Ни один байт не попадает в рабочий каталог до прохождения всех сит.

1. **Расширение** — закрытый список (`docx, xlsx, doc, xls, pdf, md, txt, csv`);
   `UPLOAD_ALLOWED_EXTENSIONS` может его только **сузить**. Отсев происходит до
   записи на диск.
2. **Размер** — пустой файл и файл сверх `MAX_UPLOAD_MB` отклоняются (413).
3. **Магические байты** — содержимое обязано соответствовать расширению:
   ZIP/OOXML, OLE2, `%PDF-`, текст (без NUL, валидный UTF-8, не MZ/ELF/PK).
   `virus.exe`, переименованный в `ТЗ.docx`, отклоняется (400 `MAGIC_MISMATCH`);
   `смета.xlsx.exe` не проходит по расширению. Заявленный `Content-Type` не
   отклоняет файл (браузеры врут), но расхождение фиксируется.
4. **SHA-256** — считается потоком, сохраняется в `documents.sha256` вместе с
   размером, вердиктом антивируса и `uploaded_by`.
5. **Антивирус** — `AV_SCAN_MODE`: `clamd` (TCP INSTREAM), `command` (внешний
   сканер: 0 — чисто, 1 — заражено), `http` (сервис проверки). **В production
   обязателен**; `disabled` допустим только вне production.
   **Fail-closed:** заражён → 422, сканер недоступен/таймаут/непонятный ответ →
   503, файл в обоих случаях удаляется. «Пропустим, антивирус лежит» — нет.

Скачивание отдаёт только файлы из каталога загрузок (путь из БД проверяется на
принадлежность `UPLOAD_ROOT`).

**Клиент.** Выгрузки закрыты токеном, поэтому прямые ссылки `<a href>` больше не
работают — файл забирается запросом с заголовком (`api.download*`,
`client/src/services/api.js`). Токен живёт в `sessionStorage` (до закрытия
вкладки, не остаётся на общем компьютере), 401 сбрасывает его и уведомляет UI.

## 9. TLS до PostgreSQL

`db/connectionTarget.js` → `sslOptionFor`:

* **production** — `rejectUnauthorized: true` всегда; `servername` берётся из
  строки подключения (нужно при работе через pooler); корневой сертификат из
  `PGSSLROOTCERT` / `DATABASE_CA_CERT_FILE` (путь) либо `DATABASE_CA_CERT`
  (PEM или base64). Нечитаемый файл сертификата — ошибка, а не тихий пропуск
  проверки;
* `sslmode=disable` и `sslmode=no-verify` в production — **ошибка** с
  машинным кодом, а не «поедем без TLS»;
* вне production поведение прежнее: TLS включён, сертификат не проверяется,
  `sslmode=disable` отключает TLS для локального кластера.

## 10. Что роняет старт в production

`assertProductionSecurity` собирает **все** проблемы сразу:

* не настроен ни один источник проверки токена;
* `AUTH_DEV_BYPASS=1`;
* режим задан, а ключ/issuer/URI к нему — нет; секрет HS короче 32 символов;
* `AUTH_JWT_AUDIENCE` пуст (примут токен соседнего сервиса того же провайдера);
* HS* в списке алгоритмов при асимметричном режиме (alg-confusion);
* `CORS_ALLOWED_ORIGINS` пуст или содержит `*`;
* `AV_SCAN_MODE=disabled` (или режим без своих параметров);
* `DATABASE_ALLOW_INSECURE_TLS=1`, `ERRORS_EXPOSE_INTERNALS=1`,
  `RATE_LIMIT_ENABLED=0`, `AUDIT_ENABLED=0`.

## 12. Чего в этом baseline НЕТ (осознанно)

* **Своего входа/сессий/паролей** — вход остаётся у корпоративного IdP, портал
  только проверяет токен.
* **Refresh-токенов и отзыва (revocation/introspection)** — доступ истекает по
  `exp`. Для мгновенного отзыва нужен `token_introspection` или короткий `exp`.
* **Общего стора лимитера** — счётчики в памяти процесса (см. §7).
* **Шифрования файлов и полей БД на покое** — это уровень диска/кластера.
