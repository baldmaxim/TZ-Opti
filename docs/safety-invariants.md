# Инварианты безопасности TZ-Opti

Свойства, которые обязаны выполняться **всегда**, независимо от UI, порядка
действий инженера и повторных запусков. Все они проверяются **на сервере**:
клиентские блокировки — только подсказка пользователю, защитой не считаются.

Общее правило: **fail-closed**. Если проверку нельзя выполнить достоверно —
операция отклоняется с явной ошибкой. Частичный результат никогда не выдаётся
как полный, ошибка никогда не проглатывается.

Статус каждого инварианта отмечен честно:
- ✅ **обеспечен** — есть код + автотест;
- ⚠️ **частично** — механизм есть, но покрыт не весь путь;
- ⬜ **не обеспечен** — сформулирован как цель следующих изменений.

---

## 1. Успех — только по persisted successful run

Стадия/прогон считается успешной, только если факт успеха **записан в БД**
(строка прогона в терминальном статусе `done` с сохранённым результатом).
Ответ HTTP 200 сам по себе успехом не является; статус в памяти процесса —
тоже. Прогон, чей процесс погиб, обязан читаться как незавершённый, а не как
успешный.

Следствия:
- клиент определяет готовность только по состоянию, прочитанному с сервера;
- прогон живёт в очереди (`analysis_jobs`/`analysis_tasks`), а не в памяти
  процесса: успех фиксируется единственным условным `UPDATE` по владельцу
  аренды — воркер, потерявший аренду, закоммитить результат не может;
- «зомби»-статусы `running` после падения сервера сбрасываются: осиротевшие
  задачи чинит reaper (возврат в очередь или `interrupted`), а стадии без
  живого задания — `stageEngine.recoverOrphanedRunningStages()` при старте;
- пустой/невалидный ответ LLM — это провал стадии, а не «успех с 0 находок».

Статус: ✅ обеспечен для стадий и конвейера (аренда + условные переходы +
`interrupted` как отдельный исход; тесты `jobsWorker.test.js`,
`jobs.integration.test.js`).

## 2. Экспорт — только при полной актуальной рецензии

Экспорт `.docx` (и производные выгрузки) допустим, только когда рецензия
покрывает **все** актуальные кластеры текущей ревизии документа и не устарела
относительно последней пересборки конвейера
(`GET /api/tenders/:id/pipeline/status` → `stale` / `needs_rebuild`).
Нерешённые кластеры или устаревший слой — отказ с указанием, чего не хватает,
а не «выгрузим что есть».

Статус: ⚠️ частично (свежесть слоёв считается и показывается; жёсткого
серверного отказа экспорта при неполной рецензии ещё нет).

## 3. Destructive edit — только по exact unique target

`delete`, `remove_from_scope`, `edit` изменяют документ **только** если целевой
диапазон найден точно и единственным образом. Нечёткое (fuzzy) совпадение,
несколько кандидатов, пустой `source_fragment` — запрещают правку: решение
уходит в Word-комментарий (`status='fallback'`) либо помечается `failed`/
`skipped` в отчёте экспорта. Молча «похоже подходит» — недопустимо.

Проверяется регресс-набором `server/test/unit/reviewExport.test.js`
(абзац / список / таблица / мультиформат / повтор текста).

Статус: ✅ обеспечен для документного слоя (fallback-путь и отчёт по каждому
решению); ⚠️ пороги толерантного матчинга (`findFragmentTolerant`) требуют
отдельного аудита.

## 4. Один источник решений

Решение по месту ТЗ живёт в одном месте: `review_decisions.cluster_id`
(этап 6–7). Preview, таблица рецензии, `.docx`, CSV/JSON/summary и review.md
читают **одно и то же** решение через `review/decisionModel.js`
(`decisionVisual` + `resolveRedaction`) и `review/clusterReviewService.js`.
Расхождение «в preview одно, в Word другое» — дефект.

Issue-level путь (`review_decisions.issue_id`) сохранён как **явный**
ограниченный fallback: включается автоматически, только когда кластерных
решений нет, и принудительно по `?source=issues`; фактический источник всегда
виден в заголовке `X-Export-Source`. Скрытых веток нет.

Статус: ✅ обеспечен (тесты `clusterReview.test.js`, `clusterExports.test.js`,
`consolidation.test.js`).

## 5. Один документ / одна ревизия на анализ и экспорт

Анализ и экспорт работают с одной и той же ревизией исходного `.docx`. Если
после анализа загружен новый файл ТЗ, результаты предыдущей ревизии не
применяются к новому документу: требуется пересборка. Экспорт всегда идёт от
исходного файла, зафиксированного за этой ревизией, а не от «последнего
загруженного».

Статус: ⬜ не обеспечен (ревизия документа сейчас не является явной сущностью;
выбирается последний `.docx` в слоте ТЗ — `exportController.getTzOriginal`).

## 6. Долгие операции восстанавливаемы

Анализ стадии и пересборка конвейера идемпотентны: повторный запуск не создаёт
дублей (id кластера детерминирован от `tenderId + cluster_key`, решения по
`cluster_id` переживают пересборку). Статус долгой операции хранится в БД,
поэтому перезапуск сервера или обрыв соединения не «теряют» и не «удваивают»
работу. Сбой шага конвейера не превращается в HTTP-ошибку молча: отчёт
`{ok, failed_step, steps[]}` показывает, что выполнено, а что `skipped`.

Обеспечивается очередью `analysis_jobs`/`analysis_tasks`:
- **не удваивает** — задачу забирает ровно один воркер (`FOR UPDATE SKIP
  LOCKED`), повторный запуск того же прогона дедуплицируется по ключу
  идемпотентности (частичный `UNIQUE`-индекс: гонку решает БД), а одновременный
  прогон одной стадии одной ревизии запрещён `pg_try_advisory_lock`;
- **не теряет** — прогресс и чекпойнт лежат в БД: после рестарта задача либо
  продолжается с последнего посчитанного сегмента ТЗ, либо (когда попытки
  исчерпаны) получает статус `interrupted`, а стадия возвращается в `open`;
- **не молчит** — исход задания (`completed`/`failed`/`cancelled`/`interrupted`)
  и число попыток видны в `GET /api/jobs/:jobId`.

Статус: ✅ обеспечен (тесты: `jobsModel.test.js`, `jobsWorker.test.js`,
`jobs.integration.test.js` — повторный запуск, два процесса-воркера, рестарт,
отсутствие дублей).

## 7. Все gates исполняет сервер

Любое ограничение (стадия заблокирована, нет ТЗ, рецензия не завершена, файл
не того формата) проверяется в контроллере/сервисе и возвращает ошибку с
кодом. UI-блокировки дублируют это для удобства и **не являются** защитой:
прямой вызов API обязан получить тот же отказ, что и заблокированная кнопка.

Статус: ⚠️ частично (проверки формата ТЗ, наличия документа и стадийных
блокировок есть; единого реестра gate-кодов пока нет).

## 8. Доступ: закрыто по умолчанию, тенант — из токена

Полное описание контура — [docs/security.md](security.md). Инвариантами здесь
считаются те свойства, нарушение которых означает утечку, а не неудобство:

- **Нет открытых маршрутов, кроме `/api/health`.** Любой другой `/api`-путь без
  Bearer-токена отвечает 401 — включая несуществующие (иначе по кодам ответа
  изучают поверхность API). Проверка: `test/unit/appSmoke.test.js`,
  `test/unit/security/httpAccess.test.js`.
- **Маршрут без правила доступа запрещён (default deny).** Право, действие и
  источник тенанта описаны в `server/security/policy.js`; отсутствие строки →
  403 `POLICY_UNMATCHED`. Проверка: `test/unit/security/policy.test.js` обходит
  ВСЕ зарегистрированные маршруты приложения.
- **Тенант субъекта — только из токена, тенант ресурса — только из БД.** Ни
  тело запроса, ни query, ни заголовок на принадлежность не влияют; списки
  ограничиваются в SQL (`WHERE tenant_id = ?`), а не после выборки.
  Межтенантное обращение → 403 `CROSS_TENANT_DENIED`.
- **Тендер без тенанта невозможен.** `tenders.tenant_id` — `NOT NULL DEFAULT`
  (`SECURITY_DEFAULT_TENANT`), поэтому даже вставка в обход контроллера (сид,
  служебный скрипт) не создаёт «ничью» строку.
- **Вложенная запись адресуется парой (тендер + id).** Middleware проверяет
  только тендер из пути, поэтому SQL для `checklist/:itemId`, `qa/:entryId`,
  `risks/custom/:customId`, `review/clusters/:clusterId` обязан ограничивать
  выборку тендером. Проверка: «чужой id вложенной записи под своим тендером»
  в `test/unit/security/httpAccess.test.js`.
- **Неизвестная роль прав не даёт.** Роли провайдера отображаются
  `AUTH_ROLE_MAP`; субъект без известной роли → 403 `NO_ROLES`.
- **Файл попадает в папку тендера только пройдя все проверки** (формат,
  сигнатура, SHA-256, антивирус). Всё, что не «однозначно чисто» — включая
  недоступный сканер — файл не принимает и удаляет из карантина.
- **Небезопасная конфигурация production не запускается.** Нет аутентификации,
  включён dev-bypass, пустой CORS-allowlist, выключенный антивирус, нестрогий
  TLS до Postgres, `ERRORS_EXPOSE_INTERNALS=1` — старт прерывается
  (`security/config.js` → `assertProductionSecurity`).
- **В production наружу не уходят внутренние детали.** 5xx → общий текст +
  `request_id`; причина отказа в доступе видна в журнале аудита, а не в ответе.

## Инварианты тестового контура

Эти проверки уже полностью автоматизированы (`npm run test:unit`):

- **Тестовый процесс не ходит в production-БД.** Цель подключения резолвится
  в `server/db/connectionTarget.js`: в тестовом процессе — только
  `TEST_DATABASE_URL`; `DATABASE_URL` не используется, а совпадение двух
  строк — ошибка `TEST_DATABASE_URL_EQUALS_PRODUCTION`. Признак тестового
  процесса даёт `utils/runtimeMode.js` по двум независимым сигналам
  (`NODE_TEST_CONTEXT` от `node --test` и `NODE_ENV=test`).
- **Юнит-тесты офлайн.** Импорт приложения и сервисов не поднимает pg-пул, не
  открывает порт и не делает сетевых вызовов (`test/unit/moduleLoad.test.js`,
  helper `test/helpers/network.js`).
- **Реальный LLM в тестах запрещён.** `chatJson` в тестовом процессе без
  установленного fake-провайдера бросает `LLM_CALL_IN_TEST_PROCESS`
  (`services/stageAnalysis/llm/openaiClient.js`, helper `test/helpers/fakeLlm.js`).
- **Skip виден.** Integration-тесты без `TEST_DATABASE_URL` помечаются `skip` с
  причиной; в строгом режиме (`npm run verify:integration`) — падают.
- **Секреты не в логах.** Строка подключения не попадает ни в текст ошибки, ни
  в HTTP-ответ (проверяется в `connectionTarget.test.js` и `appSmoke.test.js`).
